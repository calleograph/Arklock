# Arklock — текущее состояние проекта

> Только актуальное состояние. Журнал изменений — HISTORY.md, изменения для пользователей — CHANGELOG.md.
> Последнее обновление: 2026-10-11 (после вложений)

## 1. Назначение

Arklock — бесплатный корпоративный менеджер паролей с открытым исходным кодом, ориентированный на безопасность, самостоятельное развёртывание и централизованное управление доступом.
Репозиторий: https://github.com/calleograph/arklock (закрытый; опубликован `main`, CI запускается). Лицензия: **AGPL-3.0-only** (решение владельца; текст в `LICENSE`).
Запрещены платные ограничения, лицензионные ключи, серверы активации, телеметрия лицензирования.

## 2. Статус

- Этап 1 (каркас) и Этап 2 (учётные записи, мастер-пароль, клиентское шифрование, личный сейф) выполнены и проверены автотестами, тестами в браузере и в CI.
- **Инфраструктурный рубеж 1** (установка, резервное копирование, обновление и откат из командной строки) реализован и проверен в CI на Ubuntu 24.04. Не реализованы: остальные разделы административной панели, расписание и удалённые хранилища копий, автоматическая настройка HTTPS/Nginx, публикация образов в GHCR, релизы.
- **Помощник обновлений и страница «Обновления и версии»** реализованы и подтверждены в CI (проверка и обновление из браузера, откат после сбоя).
- **Рабочее пространство** (общие хранилища, роли, круги, гранты, папки, записи, ревизии, корзина, импорт/экспорт, ссылки передачи, инспектор, вложения, ротация ключа) реализовано и проверено автотестами и тестами в браузере; в CI подтверждено до вложений включительно (коммит cbf3a79).
- **Двухфакторная аутентификация** (TOTP, резервные коды, политика обязательности) реализована и проверена тестами API и в браузере.
- **Токены API и консольный клиент `arklock`** реализованы и проверены тестами (docs/CLI.md).
- **Панель администрирования**: обзор, ресурсы, контейнеры, резервные копии (в том числе расписание, скачивание, восстановление), журналы, хранилища, диагностика, сертификаты, почта — реализованы и проверены тестами API, сценарием в браузере и (помощник) в CI.
- Впереди: WebAuthn, LDAP/LDAPS/AD, SSO, API-токены и CLI, расширение браузера, мобильный доступ (PWA), оставшиеся разделы панели (ресурсы, контейнеры, журналы, резервные копии, диагностика, сертификаты, SMTP, хранилища), приглашения, политики паролей по хранилищам.
- Прототип **не пригоден для хранения реальных секретов**: криптографическая архитектура не проходила независимую проверку.

## 3. Технологии

Node.js 24, TypeScript 5.9 strict (ESM), npm workspaces. Backend: Fastify 5, Zod 4, Drizzle ORM 0.45 (миграции drizzle-kit), PostgreSQL 16 (прод) / PGlite (разработка и тесты). Frontend: Vue 3, Pinia, Vue Router 4, vue-i18n 11, Vite 8, Tailwind CSS 4. Криптография: WebCrypto + Argon2id (`hash-wasm`). Тесты: Vitest 4, Playwright. Качество: ESLint 9, Prettier, vue-tsc, shellcheck. Развёртывание: Docker, Compose, Bash-сценарии (GnuPG для шифрования копий). CI: GitHub Actions.

Размещение на сервере: программа `/opt/arklock` (git-клон тега), конфигурация `/etc/arklock/arklock.env` (600) и `backup.key` (600, отдельно от копий), данные `/var/lib/arklock` (`backups`, `state`, `logs`, `updater`, `tmp`, `blobs`), PostgreSQL в именованном томе compose-проекта. ## 5. Конфигурация (переменные окружения)

API: `DATABASE_URL`, `APP_SECRET` (≥32), `BLOB_DIR` (каталог зашифрованных вложений; пусто — вложения отключены; в контейнере `/blobs`), `BOOTSTRAP_TOKEN` (одноразовый код создания первого администратора; без него в production первый администратор не создаётся), `PORT`, `HOST`, `LOG_LEVEL`, `WEB_DIST`, `TRUSTED_PROXY_HOPS`, `SESSION_IDLE_HOURS`, `SESSION_MAX_DAYS`, `LOGIN_MAX_ATTEMPTS`, `LOGIN_WINDOW_MINUTES`, `UPDATE_CHANNEL`, `APP_VERSION`/`APP_GIT_COMMIT`/`APP_BUILT_AT`. Установка: `COMPOSE_PROJECT_NAME`, `INSTALL_PROFILE`, `INSTALL_DIR`, `DATA_ROOT`, `APP_PORT`, `APP_PUBLIC_URL`, `POSTGRES_PASSWORD`, `ARKLOCK_IMAGE`, `BACKUP_KEY_FILE`. Сценарии читают файл окружения разбором строк (не исполняют). Режим регистрации после первого администратора — настройка `registration.mode` (`open`), по умолчанию регистрация закрыта.

## 6. Реализовано и проверено

- **Криптоядро** (39 тестов), **API** (149 тестов), **CLI** (9 тестов), **клиент**, **браузерные тесты** (accounts, updates, workspace — 9 сценариев; локально Edge, в CI Chromium). Подробности — `docs/security/cryptography.md`, `docs/api/README.md`.
- **Модель доступа**: роли хранилища + круги + гранты на папки/записи (чтение, запись, управление; срок; наследование); нет доступа — 404; ревизии и корзина проверяют текущий доступ.
- **Ключи**: ключ хранилища выдаётся запечатанным и подписанным; журнал ключей с цепочкой хэшей; закрепление ключей на клиенте; ротация одной транзакцией с проверкой полноты (записи, ревизии, ветви, вложения) и подписей.
- **MFA**: TOTP (секрет зашифрован на сервере), одноразовые резервные коды (HMAC), вызов без сессии до проверки кода, защита от повтора шага, политика `security.mfaRequired`.
- **Вложения**: шифрование на клиенте (куски 1 МиБ, AES-256-GCM, контекст с номером куска и признаком последнего); ключ вложения под ключом хранилища, метаданные зашифрованы; файлы в `BLOB_DIR`; квоты в настройках (`storage.attachmentMaxMiB`, `storage.vaultQuotaMiB`); сверка хранилища с базой; резервная копия включает вложения.
- **Установщик** (`install.sh`): проверка ОС (Ubuntu 24.04, Debian 12), архитектуры, памяти, места; профили standalone/shared-host; установка Docker и пакетов только в standalone; подбор свободного порта; секреты генерируются один раз; повторный запуск не меняет секреты (проверено хэшами); `--dry-run` ничего не создаёт; самозагрузка из репозитория по тегу; отказ от `main` без `--allow-unreleased`.
- **Резервное копирование** (`backup.sh`, `restore.sh`): дамп БД + конфигурация + манифест, GnuPG AES-256, ключ отдельно; проверка после создания; повреждённая копия отвергается; восстановление после полного уничтожения БД возвращает доступ тому же пользователю к той же записи (CI).
- **Обновление** (`update.sh`, `rollback.sh`, `check-updates.sh`): резервная копия перед обновлением, образ работающей версии сохраняется, сборка до переключения, автоматическое восстановление; откат отказывает при изменённой схеме (`--with-restore` — через копию). Проверенные в CI сценарии: миграция, сбойная миграция, сбойная сборка, недоступный репозиторий.
- **Диагностика**: verify, preflight, smoke-test, status, logs (маскирование), diag (маскирование, проверено), repair (только безопасные действия).
- **CI** (9 задач, все зелёные на последнем коммите): форматирование/линтер/типы/тесты, браузерные тесты, аудит зависимостей и лицензий, проверка репозитория и истории на секреты, shellcheck, контейнерная интеграция (регистрация, запись, пересоздание, pg_dump/pg_restore, секреты в слоях и логах), установщик на чистом раннере, shared-host рядом с чужими контейнерами, цепочка обновления.

## 7. Не проверено / ограничения

- Debian 12; реальный сервер и перезагрузка; восстановление на другом сервере (проверено только на том же хосте после уничтожения тома); прерывание процесса обновления; нехватка места; недоступность БД во время операций; истечение сертификатов.
- Образ собирается на сервере; GHCR, digest, подписи тегов и релизные контрольные суммы не реализованы. Репозиторий закрыт, поэтому публичная команда установки по ссылке пока не работает.
- Нет: WebAuthn, LDAP/AD, SSO, расширения браузера, PWA, разделов панели «LDAP» и «SSO», удалённых хранилищ копий (S3/SMB), проверки сертификатов по произвольным узлам, настройки HTTPS/Nginx установщиком. Файл вложения целиком держится в памяти браузера (предел — настройка, не более 512 МиБ).
- Ограничитель попыток входа работает в памяти процесса (один экземпляр API); Argon2id выполняется в основном потоке браузера (около секунды).
- Независимая проверка криптографии не проводилась. Вложения и резервная копия: блобы копируются после дампа БД (возможны лишние файлы, их убирает сверка).

## 8. Дорожная карта

Ближайшее: помощник обновлений (отдельная служба с белым списком операций, обмен через каталог), административная панель (состояние, ресурсы, контейнеры, журналы, резервное копирование, обновления, диагностика) с рабочими бэкендами, проверка на Debian 12 и расписание копий, затем Argon2id в Web Worker и Этап 3 (папки, ревизии, корзина, вложения, импорт/экспорт), Этап 4 (общие хранилища, роли, MFA, LDAP, аудит/SIEM), публикация образов и релизов, независимая проверка криптографии.

# Резервное копирование и восстановление

Статус проверки: создание, проверка, отказ при повреждении и восстановление после полного уничтожения БД проверяются в CI (задача `installer`). Восстановление на **другом** чистом сервере, расписание, S3/SMB и раздел веб-панели **не реализованы / не проверены**.

## Что входит в копию

Один зашифрованный файл `*.bak.gpg` (GnuPG, AES-256, парольная фраза из `BACKUP_KEY_FILE`) с:

- дампом PostgreSQL: учётные записи, зашифрованные клиентом записи, зашифрованные закрытые ключи пользователей, настройки, журнал;
- файлом конфигурации `arklock.env`;
- манифестом (версия, число миграций, контрольная сумма дампа). Рядом лежит `*.bak.gpg.json` с контрольной суммой файла (без секретов).

**Для менеджера паролей это главное:** пользователи шифруют данные мастер-паролями на клиенте; ключи пользователей находятся в самой БД. Поэтому дамп восстанавливает доступ ко всем секретам — пользователи входят прежними мастер-паролями. Это проверяется в CI: после уничтожения БД и восстановления тот же пользователь расшифровывает ту же запись.

## Ключ резервного шифрования

Создаётся установщиком: `/etc/arklock/backup.key` (права 600). Он **хранится отдельно от копий** и не входит в каталог данных. **Скопируйте его в надёжное место вне сервера** — без него копии не расшифровать.

## Команды

```bash
sudo scripts/backup.sh [--keep 14] [--label имя]     # создать копию (проверяется сразу после создания)
sudo scripts/backup.sh --verify ФАЙЛ                 # проверить существующую копию (расшифровка, контрольная сумма, читаемость дампа)
sudo scripts/backup.sh --restore-test ФАЙЛ           # пробное восстановление во временную базу и сверка; рабочая база не затрагивается
sudo scripts/restore.sh ФАЙЛ [--yes]                 # восстановить (работает без веб-приложения)
```

Пробное восстановление расшифровывает копию, восстанавливает дамп во временную базу `arklock_restore_test_<номер>` того же PostgreSQL, сверяет число миграций с манифестом копии, сообщает число учётных записей, сейфов, записей и ключей и удаляет временную базу (в том числе при ошибке). Записи остаются зашифрованными: расшифровать их могут только сотрудники своими ключами, поэтому сервер проверяет восстановимость данных, а не их содержимое. Кнопка «Проверить» у копии в веб-панели выполняет именно пробное восстановление; после создания каждой копии автоматически выполняется быстрая проверка (`--verify`). Временной базе нужно столько же места на диске, сколько рабочей.

Восстановление: проверяет копию, сверяет версию миграций (копия новее установленного приложения — отказ), требует подтверждение, создаёт **аварийную копию** текущего состояния (метка `pre-restore`), пересоздаёт БД, загружает данные, запускает приложение. Файл `arklock.env` текущего сервера не заменяется.

### Перенос на новый сервер

1. `install.sh` на новом сервере (тот же профиль).
2. Скопировать ключ резервного шифрования в `/etc/arklock/backup.key` (права 600) и файл копии в `DATA_ROOT/backups`.
3. `sudo scripts/restore.sh ФАЙЛ`.

## Ротация и место

`--keep N` оставляет N последних копий проекта (по умолчанию 14). Перед созданием проверяется свободное место.

## Удалённое хранилище копий (S3 и SMB)

Копии можно отправлять на S3-совместимое хранилище (AWS S3, MinIO, Ceph, Yandex Object Storage и др.) или на общую папку SMB/CIFS. Копия **шифруется до отправки** (GnuPG, AES-256, ключ — `backup.key`, хранится отдельно), поэтому хранилище видит только шифртекст.

**Настройка в панели** — Администрирование → Резервные копии → «Удалённое хранилище»: тип, адрес, учётные данные, папка внутри хранилища, число хранимых копий, автоматическая отправка каждой новой копии (ручной и по расписанию). Кнопки: проверка соединения (пробный объект: запись, чтение, сверка, удаление), отправка выбранной копии, список копий на хранилище, проверка целостности, загрузка копии на сервер, удаление, стирание настройки. Сохранение, удаление, загрузка и стирание требуют повторного ввода мастер-пароля.

**Защита секретов.** Секреты подключения не хранятся в базе данных Arklock и не попадают в её резервные копии. Панель передаёт их помощнику одним файлом с правами 600 (значения в base64; файл существует до принятия помощником и затем стирается); помощник сохраняет их в `remote.conf` рядом с файлом окружения (права 600, владелец root). Секреты не показываются в панели и командах, не передаются в параметрах процессов (заголовки отдаются curl через файл настроек во временном каталоге 700), не пишутся в журналы и снимки состояния. Оставьте поле секрета пустым, чтобы сохранить прежний.

**Целостность.** После отправки проверяется размер на стороне хранилища, затем копия читается обратно потоком, и её SHA-256 сверяется с описанием (`.json`, которое отправляется вместе с копией; для S3 хэш дополнительно записан в метаданные объекта). Тот же контроль — по кнопке «Проверить»; при загрузке на сервер повреждённая при хранении копия не выдаётся за годную. Файлы больше 100 МиБ уходят многочастной загрузкой (части по 64 МиБ; при сбое загрузка отменяется, неполный объект не остаётся).

**Ротация.** После каждой успешной отправки на хранилище остаются N последних копий этого проекта (по имени), остальные удаляются вместе с описаниями; копии других проектов и сторонние файлы не затрагиваются. Ротация локальных копий (расписание) работает отдельно.

**Расписание.** Копии по расписанию создаёт помощник (раздел «Расписание»); при включённой автоматической отправке каждая из них сразу уходит на хранилище. Если отправка не удалась, локальная копия остаётся, итог операции явно сообщает об ошибке, а панель показывает результат последней отправки.

**Командная строка** (работает без веб-приложения и на новом сервере):

```bash
sudo scripts/remote.sh configure            # интерактивно (или --from-env и переменные ARKLOCK_REMOTE_*)
sudo scripts/remote.sh test | list | verify ИМЯ | pull ИМЯ [КАТАЛОГ] | push ФАЙЛ | prune N | delete ИМЯ | clear
sudo scripts/restore.sh --remote ИМЯ        # взять копию с хранилища и восстановить
```

### Восстановление на другом сервере из удалённой копии

1. `install.sh` на новом сервере (тот же профиль).
2. Скопировать ключ резервного шифрования в `/etc/arklock/backup.key` (права 600). Ключ хранится отдельно от копий — без него копию не расшифровать.
3. `sudo scripts/remote.sh configure` — ввести адрес и учётные данные хранилища (секреты прежнего сервера сюда не переносятся).
4. `sudo scripts/remote.sh list` — выбрать копию; `sudo scripts/restore.sh --remote ИМЯ`.

CI проверяет это на чистом сервере: копия уходит на S3-сервер Scality CloudServer, локальная копия и настройка стираются, база уничтожается, после чего копия берётся с хранилища и данные восстанавливаются (тот же пользователь расшифровывает ту же запись).

**Ограничения.** SMB: используется `smbclient` (пакет `smbclient`), шифрование SMB 3 включено по умолчанию (`encrypt`); проверка выполняется на Samba в CI, с Windows Server и NAS разных производителей не проверялась. S3: подпись запросов — AWS Signature V4, адресация по пути по умолчанию (виртуальные хосты — `path_style=0`); проверено на Scality CloudServer (в CI) и тестовом сервере с независимой проверкой подписи, на AWS S3, Ceph и облачных сервисах не проверялось. Блокировки объектов (WORM) и версионирование хранилища из Arklock не настраиваются.

# Вход по SAML 2.0

Arklock работает как поставщик услуг (SP) для корпоративных провайдеров идентификации (IdP): Entra ID, ADFS, Okta, Keycloak, Shibboleth и других, поддерживающих SAML 2.0 Web Browser SSO. Провайдер подтверждает, кто пользователь; **мастер-пароль остаётся отдельным** и только расшифровывает данные в браузере, поэтому провайдер и сервер Arklock не получают доступа к содержимому хранилищ.

## Настройка

1. Задайте публичный адрес `APP_PUBLIC_URL` (без него SAML включить нельзя).
2. Администрирование → **SAML 2.0**. В верхнем блоке показаны данные Arklock для регистрации у провайдера: идентификатор (Entity ID), адрес приёма ответов ACS (HTTP-POST), адрес единого выхода и ссылка на метаданные поставщика услуг. Метаданные доступны без входа — их можно передать администратору провайдера.
3. Импортируйте метаданные провайдера (вставьте XML или укажите адрес) — форма заполнится: идентификатор, адрес входа, адрес выхода, сертификаты подписи, формат NameID. Всё можно ввести и вручную.
4. Сопоставление: атрибуты почты, имени, идентификатора (по умолчанию — NameID) и групп; сопоставление групп провайдера кругам Arklock; необязательный список групп, членам которых разрешён вход; допустимые домены почты.
5. **Проверить настройку**: сертификаты (срок, размер ключа), доступность адреса входа, построение запроса, соответствие кругов. Сохраните и включите.

## Что проверяется при каждом входе

| Проверка                                    | Как                                                                                                  |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Подпись                                     | XML-подпись утверждения (или ответа) проверяется настроенными сертификатами провайдера; `KeyInfo` из самого документа не используется. Подмена содержимого после подписания, дополнительные утверждения, несколько подписей отвергаются |
| Алгоритм                                    | SHA-1 отвергается, пока администратор явно не разрешит; проверяется и подпись внутри зашифрованного утверждения |
| Статус и издатель                           | Успешный статус ответа; издатель ответа и утверждения совпадает с настроенным провайдером               |
| Срок и часы                                 | `NotBefore`/`NotOnOrAfter` утверждения и подтверждения субъекта, допустимое расхождение часов — в настройках |
| Аудитория и получатель                      | Утверждение выдано для идентификатора Arklock и адреса ACS                                           |
| Привязка к запросу                          | `InResponseTo` совпадает с выданным запросом; запрос действует один раз и десять минут                |
| Одноразовость                               | Состояние входа (RelayState) и идентификатор утверждения принимаются один раз                        |
| Привязка к браузеру                         | Вход начинается во вкладке, где хранится случайное значение (в sessionStorage), серверу уходит его хэш; билет возврата принимается только вместе с ним. Чужой браузер не может навязать вход |
| Ограничение попыток                         | Неудачные ответы с одного адреса ограничиваются по числу в окне                                       |
| Почта и домен                               | Адрес берётся из атрибута (или NameID в формате email), домен проверяется по списку                   |
| Учётная запись другого происхождения        | Существующая локальная учётная запись с тем же адресом не перехватывается                              |

Подпись запросов и расшифровка: кнопка **Создать сертификат поставщика услуг** создаёт пару RSA-2048 (10 лет). Закрытый ключ хранится на сервере только в запечатанном виде и не возвращается API. Он нужен для подписи запросов на вход (необязательно) и для **зашифрованных утверждений**; сертификат попадает в метаданные. После замены сертификата загрузите новые метаданные у провайдера.

Ответы по инициативе провайдера (без запроса Arklock) по умолчанию отвергаются; их можно разрешить в настройках — это снижает защиту, так как билет нельзя привязать к браузеру (повторное использование утверждения всё равно блокируется).

## Пользователи и группы

- Первый вход создаёт учётную запись (если разрешено): адрес и имя берутся от провайдера, пользователь сам задаёт мастер-пароль и получает код восстановления. Внешний идентификатор — `<идентификатор провайдера>|<NameID или атрибут>`.
- Группы провайдера сопоставляются кругам Arklock и **пересчитываются при каждом входе**: пользователь, исключённый из группы, теряет членство в круге (и права, полученные через него).
- Если задан список групп для входа и пользователь ни в одну не входит, вход отклоняется, а его действующие сеансы немедленно завершаются.
- Второй фактор Arklock (TOTP, ключи доступа) продолжает действовать поверх входа через провайдера, если он включён у пользователя или обязателен политикой.

## Отзыв доступа

Доступ можно закрыть на любом уровне:

- в провайдере: запрос единого выхода (подписанный LogoutRequest; HTTP-POST проверен автотестом, HTTP-Redirect реализован, но автотестом не покрыт) на адрес выхода Arklock завершает все сеансы пользователя; запрос без подписи или с чужой подписью отвергается;
- по группам: исключение из требуемой группы закрывает вход и сеансы при следующей попытке;
- по времени: «Предельная длительность сеанса вошедших по SAML» — по истечении провайдер спрашивается снова;
- в Arklock: администратор отключает пользователя или завершает его сеансы (Пользователи).

Единый выход, начатый со стороны Arklock (выход из провайдера при выходе из приложения), не выполняется: выход из Arklock завершает только сеансы Arklock.

## Сертификаты

- Для проверки подписи используются только сертификаты, которые сейчас действуют и имеют достаточный ключ (RSA ≥ 2048 бит, EC P-256/384/521). Истёкший, ещё не действующий и слабый сертификаты не принимаются при сохранении; если все сертификаты истекли после сохранения, вход останавливается с понятной причиной (`idp_cert_expired`), а проверка настройки сообщает об ошибке.
- Замена сертификата провайдера без простоя: добавьте новый сертификат рядом со старым, после перехода провайдера удалите старый.
- Предупреждение за 30 дней до окончания показывается в панели и в проверке настройки.

## Ошибки и журнал

Пользователь видит короткую причину (подпись, срок, аудитория, издатель, группа, домен и т. д.). В журнале событий — `auth.saml.failed` с кодом причины, адресом и без содержимого ответа; `auth.saml.revoked`, `auth.saml.logout`, `admin.saml.save`, `admin.saml.sp-cert` фиксируют отзыв и изменения настроек.

## Ограничения

- Поддерживается привязка HTTP-Redirect для запроса на вход и HTTP-POST для ответа (то, что используют корпоративные провайдеры). Artifact-привязка и вход нескольких провайдеров одновременно не поддерживаются: настраивается один провайдер.
- Метаданные провайдера по адресу читаются без проверки их подписи; сверяйте отпечатки сертификатов, которые показывает панель.
- Проверка на стенде с настоящими Entra ID / ADFS / Okta / Keycloak не проводилась; интеграция проверена на тестовом провайдере, который формирует и подписывает ответы по спецификации (тесты API и сценарий в браузере).

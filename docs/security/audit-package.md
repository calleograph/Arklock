# Материалы для независимой проверки криптографии

Документ для внешнего специалиста по безопасности: что проверять, где это в коде, чем подтверждается и что остаётся неизвестным. Он описывает **фактическое** состояние; независимая проверка **не проводилась**, до неё Arklock не следует использовать для хранения реальных секретов. Общее описание — [cryptography.md](cryptography.md), угрозы — [threat-model.md](threat-model.md).

## 1. Границы проверки

В охвате (приоритет сверху вниз):

1. `packages/crypto` — все примитивы и протоколы (≈ 1,5 тыс. строк): AEAD, Argon2id, ECDH-запечатывание, подписи, журнал ключей, вложения, ссылки передачи, восстановление.
2. `packages/client` и `apps/web/src/stores/workspace.ts`, `apps/web/src/services/account.ts` — применение примитивов: выдача и проверка ключей хранилищ, ротация, закрепление журнала ключей.
3. `apps/api/src/routes/{auth,vaults,content,attachments,sharing}.ts`, `access.ts`, `perms.ts` — что сервер принимает, хранит и выдаёт; проверки прав.
4. Вне охвата: Docker/Nginx-развёртывание, сторонние библиотеки (перечислены в разделе 8), расширение браузера и приложения для телефона (используют те же функции `packages/crypto`/`packages/client`).

Не заявляется: защита от скомпрометированного клиента (браузер, расширение, подменённый JS), от аппаратных атак и от побочных каналов в JavaScript.

## 2. Активы и доверие

| Актив                                            | Где живёт                                                  | Кому доверяем                                          |
| ------------------------------------------------ | ---------------------------------------------------------- | ------------------------------------------------------ |
| Мастер-пароль                                    | только в памяти клиента во время ввода                      | пользователь, клиент                                   |
| Закрытые ключи аккаунта (ECDH, ECDSA)            | на сервере, зашифрованные `wrapKey`; в памяти клиента       | клиент                                                 |
| Ключ восстановления                              | у пользователя (код); на сервере — только производные       | пользователь                                           |
| Ключ хранилища VK, ключи записей EK              | запечатаны открытыми ключами участников; в памяти клиента   | участники хранилища                                    |
| Данные записей, названия папок, вложения         | на сервере только шифртекст                                 | —                                                      |
| Метаданные (идентификаторы, время, состав, размер) | на сервере открытым текстом                                | сервер (честный, но любопытный — см. раздел 7)         |

Сервер считается **не доверенным для конфиденциальности и подлинности ключей**, но доверенным для доступности и для проверки прав. Всё, что требует подлинности ключа участника, проверяется клиентом (разделы 4–5).

## 3. Примитивы и параметры

| Что | Алгоритм и параметры | Код |
| --- | --- | --- |
| Шифрование | AES-256-GCM, nonce 96 бит (CSPRNG, на каждое шифрование), тег 128 бит; AAD обязателен | `aead.ts` |
| Контекст (AAD) | `тип|JSON-массив частей`; границы частей однозначны | `context.ts` |
| Пароль → ключи | Argon2id (`hash-wasm`, в Web Worker), по умолчанию m=64 МиБ, t=3, p=1; сервер отклоняет параметры слабее m=19 МиБ, t=2; соль и идентификатор аккаунта входят в вывод | `kdf.ts` |
| Разделение ключей | HKDF-SHA-256, метки `arklock/v1/wrap`, `arklock/v1/auth` | `kdf.ts` |
| Запечатывание | ECDH P-256 с эфемерным ключом отправителя → HKDF → AES-256-GCM; формат `as1.<эфемерный ключ>.<ak1…>` | `asym.ts` |
| Подписи | ECDSA P-256/SHA-256 (WebCrypto) | `sign.ts` |
| Хэши | SHA-256 | `sign.ts` |
| Вложения | AES-256-GCM по кадрам 1 МиБ; AAD = `att-chunk|id|индекс|последний` | `attachment.ts` |
| Ссылки передачи | ключ только во фрагменте адреса; необязательная кодовая фраза через Argon2id | `handoff.ts` |
| Восстановление | ключ 256 бит, код с контрольной суммой; отдельное доказательство владения | `recovery.ts` |
| Токены сессий и API | 256-битный случайный токен, на сервере хранится SHA-256 | `apps/api/src/auth/session.ts` |
| Секреты настроек сервера (LDAP, OIDC, SMTP, ключ SAML) | AES-256-GCM ключом из `APP_SECRET`, контекст по назначению | `apps/api/src/secretbox.ts` |

Собственных примитивов нет. Версия формата входит в префикс шифртекста (`ak1`, `as1`).

## 4. Протоколы

### 4.1 Регистрация и вход

1. Клиент создаёт случайную соль, выводит `authKey` и `wrapKey` (раздел 3), генерирует пары ECDH и ECDSA, шифрует закрытые ключи `wrapKey` и ключом восстановления, отправляет открытые ключи, шифртексты и **`authKey`** (не пароль).
2. Сервер хранит HMAC-SHA-256 от `authKey` с индивидуальной солью, сравнивает за постоянное время, ограничивает попытки по адресу и IP, на неизвестные адреса отвечает за то же время (фиктивный хэш).
3. Вход: клиент получает параметры KDF, повторяет вывод, предъявляет `authKey`; при включённом втором факторе сессия выдаётся только после его проверки. Сессия — случайный токен; на сервере SHA-256; срок и простой ограничены (`SESSION_MAX_DAYS=7`, `SESSION_IDLE_HOURS=12`); смена пароля завершает остальные сеансы, изменение роли и отключение пользователя — все его сеансы.
4. Входы через LDAP/OIDC/SAML подтверждают личность, но **не дают ключей**: мастер-пароль для шифрования задаёт пользователь, провайдер его не знает. Билет возврата после внешнего входа привязан к браузеру (хэш проверочного значения при старте, значение — в sessionStorage вкладки).

Файлы: `routes/auth.ts`, `auth/session.ts`, `packages/client/src/login.ts`, `apps/web/src/services/account.ts`.

### 4.2 Ключ хранилища и его выдача участникам (защита от подмены открытых ключей)

- VK — 256 бит, создаётся клиентом. Участнику VK выдаётся запечатанным его открытым ключом ECDH; контекст запечатывания включает идентификаторы хранилища и получателя и версию ключа.
- **Подпись выдачи.** Выдающий (администратор хранилища) подписывает ECDSA контекст `vault-key-grant|vaultId|memberId|keyVersion` и хэш запечатанного значения. Получатель проверяет подпись открытым ключом подписи выдающего **до** использования ключа. Сервер не может подставить чужой ключ, другого получателя или другую версию.
- **Журнал ключей (прозрачность).** Каждое появление или смена пары открытых ключей пользователя — запись цепочки `hash = SHA-256(ctx("key-log", prevHash, userId, encPublic, signPublic))`. Клиент проверяет цепочку целиком (`verifyKeyLog`), **закрепляет** последнюю известную запись (`arklock.keylog.<userId>` в localStorage) и отвергает журнал, в котором закреплённая запись изменена, укорочена или переставлена. Подмена открытого ключа сервером обнаруживается при следующем входе любого участника, кроме самого первого знакомства (trust on first use).
- **Сверка отпечатков.** `fingerprint(encPublic, signPublic)` — 12 групп по 4 hex, для сверки вне системы; интерфейс показывает отпечатки участников при выдаче ключа.

Остаётся: до первого закрепления клиент доверяет журналу, который выдал сервер (TOFU); для высоких требований нужна сверка отпечатков по независимому каналу.

Код: `sign.ts`, `vault.ts`, `packages/client/src/session.ts` (`openAccount`), `apps/web/src/stores/workspace.ts` (`loadKeyLog`, `addMember`).

### 4.3 Записи и вложения

- Запись: ключ записи EK (256 бит) оборачивается VK; содержимое шифруется EK; AAD привязывает шифртекст к `vaultId`, `entryId`, версии ключа — сервер не может подменить запись другой.
- Названия папок шифруются VK (контекст с идентификаторами).
- Вложение: имя и тип — в зашифрованном заголовке; тело — кадры по 1 МиБ, каждый со своим nonce; AAD фиксирует идентификатор вложения, номер кадра и признак последнего — усечение, перестановка, дублирование и «отрезанный хвост» обнаруживаются (`AttachmentDecryptor`). Загрузка и скачивание идут потоком, файл целиком в памяти не держится.

### 4.4 Отзыв доступа и ротация

Отзыв прекращает выдачу данных и новых ключей (проверка на сервере). Против уже скопированного данных отзыв бессилен — поэтому после отзыва интерфейс предлагает **ротацию**: клиент создаёт новый VK и перешифровывает EK, названия папок, ревизии, ветви, корзину и вложения (потоково); старый VK новые данные не открывает. Новый VK выдаётся оставшимся участникам теми же подписанными выдачами.

### 4.5 Восстановление и смена пароля

Смена пароля — перешифрование закрытых ключей новым `wrapKey` (ключи аккаунта не меняются). Восстановление: ключ восстановления расшифровывает копию закрытых ключей; сервер проверяет отдельное доказательство владения. Потеря и мастер-пароля, и ключа восстановления означает потерю данных — осознанное свойство.

### 4.6 Ссылки передачи

Одноразовая ссылка: секрет шифруется случайным ключом, который находится только во фрагменте адреса (в журналы сервера не попадает); необязательная кодовая фраза усиливает защиту. Просмотр засчитывается сервером; ссылка гаснет по числу просмотров, сроку или отзыву.

## 6. Известные ограничения и вопросы к проверяющему

1. TOFU журнала ключей (раздел 4.2). Достаточно ли сверки отпечатков вне системы, или нужен подписанный контрольный пункт сервера (checkpoint)?
2. Один и тот же `wrapKey` защищает оба закрытых ключа аккаунта (ECDH и ECDSA) — при компрометации мастер-пароля раскрываются оба; разделение по назначению (отдельные производные) возможно без смены формата.
3. Запечатывание без аутентификации отправителя используется только там, где подлинность обеспечивает отдельная подпись (выдача ключа хранилища); для ссылок передачи отправитель не аутентифицируется намеренно.
4. Метаданные (состав участников, названия общих хранилищ, размеры и время) видны серверу — см. threat-model.
5. Затирание памяти в JavaScript не гарантируется.
6. Целостность доставляемого клиента (JS) зависит от сервера; защита — CSP, отсутствие внешних скриптов. Подписанные сборки и контроль целостности клиента (SRI/подпись релиза) — задача релизного конвейера.
7. Протокол ротации и выдачи ключей описан здесь, но формальная модель (ProVerif/Tamarin) не строилась.
8. Расширение браузера хранит сессию и ключи в `storage.session` (память браузера); мобильные нативные клиенты не реализованы.

## 7. Как воспроизвести проверки

```bash
npm ci
npm run build -w @arklock/crypto -w @arklock/contracts
npx vitest run --project crypto          # тесты криптографии (включая негативные)
npx vitest run --project api             # тесты сервера (права, ключи, вложения, роли, вход)
E2E_CHANNEL=chrome npx playwright test   # сквозные сценарии в браузере
```

Исходный код читается без сборки; точки входа — `packages/crypto/src/index.ts` и протоколы в `packages/client/src/session.ts`.

| Библиотека | Роль |

# Криптографическая модель Arklock

Статус: **черновик реализации, независимая проверка не проводилась.** Продукт нельзя считать пригодным для производственного хранения секретов, пока проверка не выполнена. Код: `packages/crypto`, тесты: `packages/crypto/test`.

## Примитивы (только стандартные, собственных нет)

| Назначение                | Алгоритм                                                                                     |
| ------------------------- | -------------------------------------------------------------------------------------------- |
| Симметричное шифрование   | AES-256-GCM, nonce 96 бит (случайный), тег 128 бит, обязательный AAD                         |
| Ключ из пароля            | Argon2id (`hash-wasm`), по умолчанию m=64 МиБ, t=3, p=1; нижняя граница m=19 МиБ, t=2       |
| Разделение ключей         | HKDF-SHA-256 с метками `arklock/v1/wrap` и `arklock/v1/auth`                                 |
| Асимметричная часть       | ECDH P-256 + HKDF-SHA-256 + AES-256-GCM («sealed box» с эфемерным ключом отправителя)        |
| Случайные числа           | `crypto.getRandomValues`                                                                     |

## Иерархия ключей

```
мастер-пароль ─Argon2id(соль + id аккаунта)→ мастер-материал ─HKDF→ wrapKey  (шифрует закрытый ключ аккаунта; сервер его не видит)
                                                              └HKDF→ authKey  (доказательство знания пароля; сервер хранит только хэш)
закрытый ключ аккаунта (ECDH P-256) — хранится на сервере зашифрованным ключом wrapKey
ключ хранилища VK (256 бит) — запечатан открытым ключом каждого участника (привязан к vaultId, userId, keyVersion)
ключ записи EK (256 бит) — шифруется ключом VK; данные записи шифруются ключом EK
```

## Формат шифртекста

`ak1.<nonce b64url>.<ciphertext||tag b64url>`; запечатанное значение: `as1.<эфемерный открытый ключ b64url>.<ak1…>`. Префикс — версия формата: смена алгоритма означает новую версию, старые значения читаются до переупаковки.

## Контекст (AAD)

Каждое шифрование включает контекст вида `тип|["часть1","часть2",…]`. Части кодируются JSON-массивом, поэтому границы однозначны: идентификаторы `a:b` + `c` и `a` + `b:c` не дают одинакового контекста (проверено тестом). Используются контексты `account-key`, `account-key-recovery`, `entry` и `entry-key` (хранилище, запись, версия ключа), `vault-key` (хранилище, участник, версия ключа) и `seal` (обёртка контекста запечатывания). Сервер не может незаметно подставить шифртекст другой записи, другого хранилища или другой версии ключа — расшифровка завершится ошибкой аутентификации (тесты в `packages/crypto` и `apps/api`).

## Вход и проверка пароля

Клиент выводит `authKey` и `wrapKey` независимо друг от друга (HKDF с разными метками). На сервер уходит только `authKey`; сервер хранит HMAC-SHA-256 от него с индивидуальной солью и сравнивает за постоянное время. `authKey` — 256-битный вывод Argon2id, поэтому подбор по утёкшей базе по стоимости равен подбору Argon2id. Параметры Argon2id хранятся для каждой учётной записи; клиент отказывается работать с параметрами ниже минимума (защита от понижения сервером), сервер не принимает регистрацию ниже минимума. На запрос параметров для несуществующего адреса сервер отдаёт детерминированные правдоподобные значения (HMAC от секрета приложения) — перебор адресов по этому запросу невозможен. Попытки входа и восстановления ограничиваются по адресу и по IP одинаково для существующих и несуществующих учётных записей.

## Восстановление доступа

При регистрации создаётся ключ восстановления (256 бит), показывается один раз в виде кода с контрольной суммой. Сервер хранит закрытый ключ аккаунта, зашифрованный этим ключом, и хэш доказательства владения (отдельная метка HKDF — из него ключ не выводится). Потеря и мастер-пароля, и ключа восстановления означает безвозвратную потерю данных: администратор прочитать данные или сбросить пароль не может. При использовании ключа восстановления выпускается новый, прежний аннулируется, все сессии завершаются. Смена мастер-пароля перешифровывает только закрытый ключ аккаунта; хранилища и записи не затрагиваются.

## Отзыв доступа

Отзыв **блокирует получение актуальных данных и новых ключей**: сервер перестаёт выдавать записи и запечатанный ключ хранилища. Он **не отзывает** то, что участник уже скопировал или расшифровал. Для чувствительных хранилищ при отзыве выполняется ротация: создаётся VK версии n+1, ключ каждой записи заменяется новым (`rewrapEntry`), VK запечатывается для оставшихся участников. Старый VK не открывает перешифрованные записи (тест `rotation`). Сами секреты (например, пароли внешних систем) пользователю следует сменить отдельно — приложение будет выводить напоминание.

## Что видит сервер

Открытые ключи, шифртекст, проверочные значения входа, метаданные (идентификаторы, время, размеры, состав участников хранилищ, названия общих хранилищ — в открытом виде). Заголовок, логин, пароль, адрес и заметки записи находятся внутри шифртекста, поэтому поиск выполняется на клиенте. Названия личных сейфов отсутствуют. Адрес электронной почты и имя пользователя сервер хранит в открытом виде (нужны для входа и администрирования).

## Ограничения

- JavaScript не гарантирует затирание памяти; `fill(0)` — мера снижения риска, не гарантия.
- Безопасность веб-клиента зависит от целостности доставляемого JS (CSP включён; подпись сборки — задача релиза).
- Скомпрометированный браузер, расширение или сервер, подменяющий клиент, обходят E2E-защиту (см. `threat-model.md`).
- Открытые ключи участников сервер выдаёт сам, но подмена обнаруживается: выдача ключа хранилища подписана выдающим (ECDSA, привязка к хранилищу, получателю, версии и значению), открытые ключи входят в хэш-цепочку журнала ключей, которую клиент проверяет и закрепляет; отпечатки показываются для сверки вне системы. Остаётся доверие при первом знакомстве (TOFU) — см. [audit-package.md](audit-package.md).
- Запечатанное значение само по себе не аутентифицирует отправителя; аутентификацию даёт отдельная подпись выдачи ключа (для ссылок передачи отправитель не аутентифицируется намеренно).
- Токен сессии хранится в sessionStorage вкладки; XSS в клиенте даст доступ к API, но не к ключам в памяти других вкладок. Меры: строгий CSP, отсутствие внешних скриптов.

## План проверки

1. Тест-векторы и негативные тесты — в CI (есть). Реализация Argon2id (hash-wasm) сверена с эталоном OpenSSL, который воспроизводит вектор RFC 9106 §5.3 (hash-wasm не поддерживает associated data, поэтому сверка выполняется на входах без AD).
2. Сквозные сценарии в настоящем браузере (Playwright): регистрация, вход, разблокировка, восстановление; проверка, что секреты не попадают в тела запросов.
3. Материалы для независимой проверки: [audit-package.md](audit-package.md) (границы, протоколы, соответствие свойств и тестов, вопросы проверяющему). Сама проверка внешним специалистом — до заявления о готовности к production.

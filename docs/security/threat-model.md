# Модель угроз (начальная версия)

Статус: черновик Этапа 1. Дополняется с каждым этапом.

## Активы

Секреты записей; закрытые ключи аккаунтов; пароли разблокировки сейфов (никогда не покидают клиента); ключи хранилищ; учётные данные интеграций (LDAP, SMTP, SIEM); журнал (Ledger); резервные копии.

## Противники и допущения

| Противник | Что может | Что мы обещаем |
| --- | --- | --- |
| Внешний сетевой атакующий | перехват, подбор входа, SSRF через настраиваемые адреса | TLS на reverse proxy, ограничение попыток, защита от SSRF, строгая валидация |
| Злоумышленник с дампом БД или копии | читает все строки | секреты зашифрованы на клиенте; без паролей разблокировки сейфов открытый текст получить нельзя; Argon2id замедляет подбор |
| Скомпрометированный сервер приложения (без подмены клиента) | читает и подменяет данные в БД | подмена шифртекста обнаруживается (AAD); открытые секреты сервер не видит |
| Скомпрометированный сервер, **подменяющий клиент** | отдаёт вредоносный JS | E2E не защищает; снижение риска — CSP, подписанные релизы, проверка целостности клиента (план) |
| Злонамеренный участник | читает всё, к чему имел доступ | отзыв + ротация ключей; уже скопированное не вернуть |
| Злонамеренный администратор | управляет пользователями, настройками, обновлениями | администратор не видит содержимое хранилищ; действия в Ledger; обновления требуют повторной проверки личности |
| Атака через цепочку поставок или обновление | подмена образа | образы по digest из фиксированного источника, подпись (план), update-agent без произвольных команд |

## Ключевые поверхности и меры

- **Настраиваемые URL** (проверка утечек, интеграции): только HTTPS, запрет внутренних адресов, metadata и loopback, перепроверка IP при каждом запросе, запрет редиректа на другой хост, лимиты времени и размера.
- **Утечки в журналах:** `req.body` и заголовки с токенами маскируются; секреты не попадают в ошибки; тест на отсутствие секретов в логах — Этап 2.
- **XSS/CSRF:** CSP без inline-скриптов, `frame-ancestors 'none'`; способ передачи токена (заголовок или SameSite-cookie с защитой от CSRF) решается в Этапе 2.
- **Обновление:** см. `docs/architecture/updater.md`.
- **Контейнер:** не root, read-only rootfs, `cap_drop: ALL`, `no-new-privileges`, БД во внутренней сети.
- **Встроенный менеджер паролей браузера.** Поле пароля в форме записи размечено `autocomplete="new-password"`, но Chromium после сохранения записи всё равно может предложить «Сохранить пароль?». Если человек согласится, секрет сейфа окажется в хранилище браузера — вне сквозного шифрования Arklock и вне его журнала и прав. Пока нет решения, проверенного в Chrome, Edge, Firefox и Safari и с экранными чтецами, администраторам стоит отключить сохранение паролей для адреса Arklock: в Firefox — политикой `PasswordManagerExceptions` (адрес Arklock), в Chromium и Edge — политикой `PasswordManagerEnabled` для управляемых браузеров или ответом «Никогда для этого сайта» в самом браузере.

## Вне охвата сейчас

Физический доступ к рабочему месту, кейлоггеры, компрометация браузера пользователя, принуждение пользователя.

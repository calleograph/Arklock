# Защита веб-приложения Arklock

Документ описывает только то, что реализовано и проверено в версии 1.80.0. Раздел администрирования: «Безопасность → Защита веб-приложения» (только главный администратор).

## Что защищает встроенный слой

| Механизм | Где | Можно ли отключить |
| --- | --- | --- |
| Серверная проверка прав на каждом объекте; чужой сейф, запись и вложение неотличимы от несуществующих (404) | API | нет |
| Проверка структуры всех входных данных (zod); значения в ошибках и журналах не повторяются | API | нет |
| Параметризованные запросы к базе | API | нет |
| Сеанс — заголовок `Authorization`, не cookie: подделка запроса с чужого сайта невозможна | API, клиент | нет |
| Content-Security-Policy без внешних скриптов, запрет вставки в чужие страницы, `nosniff`, `Referrer-Policy` | API | нет |
| Защита входа от подбора: адрес, пара «адрес + запись», запись по всем адресам; дополнительная проверка; временные ограничения | API | нет (настраиваются пороги в безопасных границах) |
| Ограничение подсетей доступа, блокировки, журнал событий, оповещения | API, панель | подсети — по решению администратора |

## Что он не защищает

- От распределённых атак на пропускную способность (DDoS): нужен внешний провайдер защиты или сетевой экран с лимитами.
- От подмены клиентского кода скомпрометированным сервером: шифрование выполняется в браузере, но JavaScript приходит с сервера. Меры снижения риска — CSP, публикация выпусков с контрольными суммами и SBOM, доступ к серверу только администраторам, HTTPS.
- От кражи разблокированного устройства сотрудника и от слабого пароля, который пользователь выбрал сам.
- Эвристики запросов (признаки SQL-инъекций и XSS) — подсказка, а не защита: настоящая защита — серверная проверка прав и параметризованные запросы.

## Защита входа и дополнительная проверка

- Ошибки считаются на сервере в скользящем окне (по умолчанию 15 минут) по трём ключам: адрес, пара «адрес + учётная запись», учётная запись по всем адресам. Состояние не зависит от cookie, вкладки, режима инкогнито и User-Agent.
- После 5 ошибок (настраивается) вход требует **дополнительной проверки**: подбор числа, при котором SHA-256 от задания и числа начинается с заданного числа нулевых бит (по умолчанию 17, растёт до 20 вместе с числом ошибок). Браузер решает задание сам в фоновом потоке, пользователь ничего не вводит, экранные дикторы читают строку состояния. Задание подписано сервером, живёт 5 минут и используется один раз (идентификатор записывается в базу, в том числе для нескольких экземпляров). Без решения сервер отказывает даже при верном пароле. Это удорожает перебор, но не отличает человека от программы: проверка дополняет ограничения, а не заменяет их.
- Адрес с 25 ошибками и пара «адрес + запись» с 10 ошибками получают временное ограничение (5 минут, повторные нарушения за сутки удваивают срок до 24 часов). Блокировки лежат в базе: переживают перезапуск и подхватываются другими экземплярами за 10 секунд. Счётчики ошибок скользящего окна хранятся в памяти процесса и после перезапуска обнуляются.
- Учётная запись целиком не блокируется: ошибки с чужих адресов включают проверку только для незнакомых адресов (с адреса, с которого за 60 суток создавался сеанс, владелец входит как обычно). Руководитель не может быть заблокирован подбором паролей с чужих адресов.
- Восстановление доступа и вход через каталог ограничиваются так же; для восстановления пороги вдвое строже.
- Ограничение: проверка кода второго фактора и вход ключом доступа по-прежнему используют прежний счётчик попыток на пользователя (10 за окно), PIN — собственный предел неверных вводов; они начинаются только после верного пароля и в новую подсистему пока не перенесены.

## Определение настоящего адреса клиента

`TRUSTED_PROXY_HOPS` (файл установки) — число reverse proxy перед Arklock. До 1.79.0 значение трактовалось на одно звено шире: при `0` заголовок `X-Forwarded-For` от любого клиента принимался, а за прокси, который **дописывает** адрес, принимался адрес, указанный клиентом. Теперь доверяется ровно указанное число звеньев справа; при `0` заголовок игнорируется.

В панели («IP-адреса и подсети → Доверенные reverse proxy») можно вместо числа звеньев задать список адресов прокси. Тогда заголовок принимается только от них. Список доверенных proxy и список разрешённых клиентских подсетей — разные настройки.

## Разрешённые подсети

Выключено по умолчанию. При включении сервер проверяет: список правил не пуст, ваш адрес проходит по правилам; изменение применяется в режиме подтверждения — если за 120 секунд администратор не нажал «Подтвердить доступ», сервер сам откатывает настройку. Адреса консоли сервера (`127.0.0.1`, `::1`) разрешены всегда. Удалить или отключить правило, под которое подпадает сам администратор, нельзя.

Аварийное выключение с консоли сервера: `scripts/admin-reset.sh access-off`. Снять все блокировки: `scripts/admin-reset.sh unblock-all`.

## Безопасная публикация в интернете

1. Завершайте TLS на reverse proxy (`scripts/proxy.sh` настраивает Nginx, HSTS и перезапись `X-Forwarded-For`).
2. Установите `TRUSTED_PROXY_HOPS` равным числу прокси или задайте список в панели. Проверьте в панели: «Ваш адрес, как его видит Arklock» должен быть вашим настоящим адресом, а не адресом прокси.
3. Закройте порт приложения (`APP_PORT`) от внешней сети: к нему должен ходить только прокси.
4. Включите второй фактор для главных администраторов («Политики безопасности»).
5. Ограничьте доступ подсетями организации, если Arklock нужен только сотрудникам.
6. Для защиты от DDoS и массовых сканирований поставьте перед Arklock NGFW или сервис защиты провайдера; встроенный слой его не заменяет.
7. Подключите syslog и оповещения: события безопасности уходят в журнал действий (и далее в syslog и вебхуки).

## Внешний WAF

Arklock ничего не передаёт внешним WAF и сервисам проверки; встроенная проверка работает без интернета. Внешний WAF ставится перед reverse proxy. Он должен: передавать настоящий адрес клиента и не допускать подмены `X-Forwarded-For`; не блокировать `/api/v1/` длинные запросы (вложения передаются частями, до 32 МиБ) и запросы обновлений. Исключения для правил OWASP CRS, которые часто срабатывают на зашифрованные данные записей (поля `ciphertext`), задаются на стороне WAF.

## События безопасности и оповещения

Журнал: «Защита веб-приложения → События безопасности». В нём нет паролей, кодов, токенов, cookie и тел запросов; неизвестные учётные записи хранятся только хэшем. Срок хранения 90 дней (7–365), не более 200 000 записей. Оповещения главным администраторам (центр уведомлений, почта при настроенном SMTP, syslog, вебхуки) об автоматических блокировках, изменении защиты и откате ограничения не чаще одного раза за 15 минут на одинаковое событие.

## Правила запросов, классы ограничений и перебор идентификаторов (1.80.0)

Вкладка «API и веб-запросы». Правила смотрят только путь и строку запроса:

| Правило | Что ловит | Режим по умолчанию |
| --- | --- | --- |
| `scan.sensitive-path` | `.env`, `.git`, `wp-login.php`, `phpmyadmin`, `*.sql`, `*.php` и подобное; 15 попаданий за 10 минут блокируют адрес | защита (ответ 404, как на любой несуществующий путь) |
| `path.traversal` | `../`, `..%2f`, `%2e%2e`, `%00`, обратная косая черта | защита (400) |
| `method.unexpected` | методы кроме GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS | защита (405) |
| `media.unexpected` | тело запроса не JSON, не `octet-stream`, не форма и не `multipart` | защита (415) |
| `inject.sql-pattern`, `inject.xss-pattern` | типовые признаки SQL-инъекции и XSS в пути и строке запроса | наблюдение |

Тела запросов не просматриваются никогда. Правила не отключаются, режимов два: «наблюдение» и «защита». Ложные срабатывания эвристик снижаются тем, что они сначала только записываются; перед включением защиты просмотрите события по правилу.

Классы ограничений (запросов в минуту на сеанс, без сеанса — на адрес): вход и восстановление 240, записи и вложения 6000, ключи и доступ 900, администрирование 900, интеграции 1800; меньше 60 задать нельзя. Не ограничиваются: проверки работоспособности, обновление и резервные копии, потоковая передача вложений. Импорт идёт обычными запросами записи, по одному на запись; на очень большом импорте предел 6000 в минуту можно поднять в панели. Импорт десятков тысяч записей на этом пределе отдельно не проверялся.

Перебор идентификаторов: 40 ответов 404/403 по сейфам, записям, вложениям, ссылкам и административным путям за 5 минут — предупреждение и оповещение; 150 — сеанс ограничивается на 5 минут.

Внешние ссылки проверены без изменения кода: страница ссылки только запрашивает сведения (счётчик просмотров не меняется), просмотр расходуется отдельным запросом после нажатия кнопки; ключ лежит во фрагменте адреса, который не отправляется серверу и в заголовок Referer; `Referrer-Policy: no-referrer`.

Импорт: не более 50 000 записей за раз, файл не больше 200 МБ; архивов в поддерживаемых форматах нет.

## Планы (не реализовано)

- Классы ограничений не разделены между экземплярами; общие счётчики в базе — отдельная работа.
- Обязательный второй фактор для главных администраторов по умолчанию на новых установках (сейчас включается политикой «Политики безопасности»).
- Перенос счётчиков второго фактора и WebAuthn в подсистему защиты входа.
- Нагрузочные испытания и проверка двух экземпляров на реальной инфраструктуре.

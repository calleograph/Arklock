# Устранение неполадок

Большинство проблем решается по этой странице. Если нужного случая здесь нет, соберите диагностический пакет и приложите его к обращению:

```bash
sudo scripts/diag.sh        # пакет без паролей и ключей
sudo scripts/status.sh      # состояние сервисов
sudo scripts/logs.sh        # журналы приложения
```

## Установка

**Установщик говорит «ОС не поддерживается».** Поддерживаются Ubuntu 22.04 и 24.04 LTS, а также Debian 12, архитектуры x86_64 и aarch64. На другой системе установка может пройти, но без проверки; её можно запустить с `ARKLOCK_ALLOW_UNSUPPORTED_OS=1`.

**Порт занят.** Установщик выбирает свободный порт, начиная с 8080. Чтобы задать свой, запустите установку с `--port 8090` (уже установленную систему можно перенастроить тем же способом).

**Нет Docker или он не запущен.** На сервере без Docker установщик ставит его сам, но в профиле `shared-host` этого не делает. Проверьте `systemctl status docker` и при необходимости `sudo systemctl start docker`.

**Установка прервалась.** Повторный запуск безопасен: секреты, тома и данные не пересоздаются.

**Не нашёл код настройки первого администратора.** Он хранится в `/etc/arklock/arklock.env` (строка `BOOTSTRAP_TOKEN=`). Файл читается только root.

## Доступ к Arklock

**С другого компьютера страница не открывается.** По умолчанию приложение слушает только адрес этого сервера. Запустите установщик снова с `--bind lan` (адрес сервера в локальной сети) либо `--bind all`. Данные сохранятся.

**Вход и регистрация по адресу вида `http://192.168.x.x` не работают.** Это правило браузера: шифрование доступно только по HTTPS или на `localhost`. Arklock в этом случае покажет причину. Настройте HTTPS: `--https self-signed` для внутренней сети, `--https letsencrypt` с доменом, либо внешний reverse proxy с TLS и параметром `--url https://ваш-адрес`.

**Вход возможен, но записи не появляются.** Обновите страницу. Если не помогло, проверьте, что время на сервере и в браузере совпадает (`timedatectl`): коды двухфакторной защиты зависят от времени.

## Учётные записи и доступ

**Исчез личный сейф после обновления.** По умолчанию личное пространство отключено. Данные и ключи не удалены. Администратор увидит наличие сейфа в Настройки → Основные → Личные сейфы и сможет временно разрешить его владельцу для переноса или экспорта. См. [порядок работы](administration/corporate-access.md).

**Нельзя отключить сотрудника: корпоративный доступ под угрозой.** Он остался единственным хранителем ключа одного или нескольких сейфов. Сначала передайте права и ключ другому сотруднику. При срочном отзыве подтверждение риска разрешает блокировку без удаления шифртекстов.

**Забыл пароль разблокировки сейфов.** Восстановить доступ можно ключом восстановления, который показан при регистрации. Без пароля разблокировки сейфов и ключа восстановления данные не открываются, и администратор их тоже не восстановит: это ожидаемое свойство шифрования. Поэтому сохраняйте ключ восстановления сразу.

**Сотрудник не видит сейф, хотя ему назначили группу.** Ключ сейфа выдаёт участник, который может управлять доступом, когда открывает сейф. Если такого участника в сети нет, доступ появится, как только он войдёт. В разделе сейфа статус покажет, что ключ ожидает выдачи.

**Администратор не может войти или главный администратор недоступен.** Оператор сервера восстанавливает доступ командой `sudo scripts/admin-reset.sh` (без веб-интерфейса): `list` — администраторы, кто главный, включены ли, есть ли второй фактор; `reset-mfa ПОЧТА`, `end-sessions ПОЧТА`, `enable ПОЧТА`, `promote ПОЧТА`; `chief ПОЧТА` — назначить главного администратора, если прежний отключён каталогом или уволен, не передав роль (прежний остаётся полным администратором). Каждое действие записывается в журнал от имени `operator`. Пароль разблокировки сейфов скрипт не сбрасывает и данные не читает.

**Заблокирован вход из-за ошибок.** После нескольких неверных попыток вход временно запрещён. Подождите указанное в сообщении время и попробуйте снова.

**Не работает вход через Active Directory / LDAP.** Используйте проверку подключения в разделе LDAP администратора и сверьте адрес сервера, порт, сертификат и учётную запись поиска. Текст ошибки из проверки лучше всего прикладывать к обращению.

## Обновления

**Обновление не проходит.** Установка и данные не меняются: при сбое Arklock возвращается на прежнюю версию или восстанавливает базу из копии, сделанной перед обновлением. Причину видно в разделе «Обновления» и в журнале (`sudo scripts/logs.sh`).

**Обновление: «в каталоге программы есть локальные изменения».** Чаще всего причина в адресе публикации: в версиях 1.0.x адрес для доступа из локальной сети вписывали прямо в `compose.yaml`. Новые версии хранят его в `APP_BIND` файла `/etc/arklock/arklock.env`. Перенос выполняется автоматически при обновлении: адрес и порт записываются в файл окружения, `compose.yaml` возвращается к версии релиза, прежняя копия сохраняется в `/var/lib/arklock/config-backups/`. Если старая версия не умеет обновляться сама, запустите новый `install.sh` с тем же `--ref` (он перенесёт адрес и запустит обновление).

Если в сообщении перечислены **другие файлы**, автоматический перенос не выполняется, ничего не меняется. Сохраните изменённые файлы (`cp`), затем верните их к версии релиза, например `git -C /opt/arklock checkout -- ИМЯ_ФАЙЛА`, и повторите обновление. Данные, пользователи и ключи находятся вне каталога программы и этим не затрагиваются.

**Адрес не совпадает.** Перенос отказывается, если в `APP_BIND` и в `compose.yaml` разные адреса. Выберите нужный адрес, укажите его в `APP_BIND`, затем повторите обновление.

**Помощник обновлений не запущен.** Раздел «Обновления» покажет это. Исправление: `sudo scripts/updater.sh repair`.

**Откат вручную.** `sudo scripts/rollback.sh` — работает, если схема базы данных с прошлой версии не менялась; иначе используйте копию из `scripts/restore.sh`.

## Резервные копии

**Копия с другого сервера не проверяется.** Копия шифруется ключом резервного шифрования исходного сервера (`/etc/arklock/backup.key`). Скопируйте этот файл на новый сервер до загрузки копии, иначе проверка покажет, что файл зашифрован другим ключом.

**Ключ резервного шифрования потерян.** Копии, созданные с ним, не открываются. Храните ключ отдельно от самих копий, например в менеджере паролей другого сервера или в сейфе.

**Не хватает места.** Резервные копии и вложения хранятся в `DATA_ROOT` (по умолчанию `/var/lib/arklock`). Проверить свободное место: `df -h /var/lib`. Срок хранения копий и корзины задаётся в настройках администратора.

## Обращение

Если проблема остаётся, создайте issue в репозитории и приложите вывод `sudo scripts/diag.sh` (без паролей и ключей). Уязвимости сообщайте по [SECURITY.md](../SECURITY.md), а не в открытом issue.

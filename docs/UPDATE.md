# Обновление и откат

Статус проверки: команды и веб-обновление автоматически проверяются в CI (задачи `update-flow` и `update-from-web`) на чистом раннере Ubuntu 24.04 с тестовыми релизами, включая обновление из браузера.

## Команды

| Команда                                     | Назначение                                                                      |
| ------------------------------------------- | ------------------------------------------------------------------------------- |
| `scripts/check-updates.sh`                  | проверка новых версий (код 10 — доступна новая, 1 — репозиторий недоступен)     |
| `scripts/update.sh [--ref vX.Y.Z] [--yes]`  | обновление до последнего (или указанного) релизного тега                        |
| `scripts/rollback.sh [--with-restore]`      | возврат к версии до последнего обновления                                       |

Обновляются только релизные теги `vX.Y.Z`; файл `VERSION` в теге обязан совпадать с тегом.

## Порядок обновления

1. Проверка требований (`preflight`), отсутствие параллельных операций. Адрес публикации, вписанный вручную в `compose.yaml` (версии 1.0.x), переносится в `APP_BIND`; других локальных изменений в каталоге программы быть не должно (см. [устранение неполадок](TROUBLESHOOTING.md#обновления)).
2. Получение тегов; при недоступности репозитория обновление прекращается, **ничего не меняется**.
3. **Зашифрованная резервная копия** перед обновлением и её проверка. Без копии обновление не продолжается.
4. Образ работающей версии сохраняется под тегом `prev-<commit>`.
5. Новая версия **собирается, пока старая продолжает работать**; сбой сборки не затрагивает работающую систему.
6. Запуск новой версии, миграции БД (применяет приложение при старте), `verify` и `smoke-test`.
7. Результат записывается в состояние и в журнал `DATA_ROOT/logs/updates.log` (без секретов).

**Место на диске.** Перед обновлением место считается по фактическим размерам: образ приложения ×2 (загрузка или сборка новой версии), база ×2 в каталоге Docker (миграции и восстановление при откате), база и вложения ×2 в каталоге данных (копия перед обновлением и её распаковка при откате), плюс запас; если каталог Docker и каталог данных на одном диске, объёмы складываются. При нехватке обновление не начинается и сообщает, сколько нужно и сколько свободно.

**Образы и кэш.** После успешного обновления — новая версия запущена, прошла проверки, образ предыдущей версии на месте — остаются два образа: текущий и предыдущий (для отката). Остальные образы этого экземпляра (прежние `prev-…`, загруженные выпуски, безымянные остатки сборок с меткой Arklock) удаляются; образ, на котором есть хотя бы один контейнер, не трогается. Кэш сборки Docker очищается, только если все контейнеры на сервере принадлежат этому экземпляру: кэш общий для всех проектов Docker. Тома, база, вложения и резервные копии очисткой не затрагиваются. При неудачном обновлении очистка не выполняется. Итог последней очистки, версия для отката, число и объём образов, размер кэша сборки — в «Обновления → Компоненты установки».

**Откат** возвращает версию, с которой выполнялось последнее обновление. Если после обновления менялась схема базы, откат требует `--with-restore` и восстанавливает копию, сделанную перед обновлением; ротация копий эту копию не удаляет.

Обновление меняет только Arklock: собирается образ выпуска с зависимостями, зафиксированными в `package-lock.json`. Оно не выполняет `npm update`, `apt upgrade` на сервере и не меняет мажорную версию PostgreSQL — переход на новую мажорную версию PostgreSQL выполняется отдельно, через резервную копию и восстановление ([резервное копирование](BACKUP_AND_RESTORE.md)).

К каждому выпуску прилагается состав зависимостей (SBOM) в форматах CycloneDX (`arklock-X.Y.Z-sbom.cdx.json`) и SPDX (`arklock-X.Y.Z-sbom.spdx.json`) с контрольными суммами в `SHA256SUMS`; уязвимости и лицензии зависимостей проверяются в CI перед выпуском (`npm audit`, `scripts/check-licenses.mjs`).

## Автоматическое восстановление при сбое

- Если схема БД не менялась (например, миграция упала целиком) — возвращаются код и образ предыдущей версии.
- Если миграции успели примениться — БД восстанавливается из копии, сделанной перед обновлением.
- Адрес публикации остаётся прежним: после возврата на версию без `APP_BIND` (1.0.x) его применяет `compose.yaml` этой версии автоматически.

## Откат

Откат кода без отката схемы БД небезопасен, поэтому `rollback.sh`:

- сравнивает число применённых миграций с известным предыдущей версии и **отказывается** (код 3), если схема изменилась;
- с `--with-restore` восстанавливает БД из копии перед обновлением (**данные, записанные после обновления, будут потеряны**) и возвращает код и образ;
- если схема не менялась — возвращает только код и образ без пересборки.

## Проверенные сценарии (CI)

Обновление с новой миграцией и сохранением данных; отказ отката при изменённой схеме; откат с восстановлением; сбойная миграция (автовосстановление); сбой сборки образа (работающая версия не затронута); недоступный репозиторий.

Не проверено: прерывание процесса обновления посреди операции (kill), нехватка места на диске, перезагрузка сервера во время обновления, проверка подписей тегов (поддерживается `ARKLOCK_REQUIRE_SIGNED_TAGS=1`, не тестировалась).

## Обновление из веб-интерфейса

Раздел «Обновления» (только администратор) показывает установленную версию, коммит и дату сборки, доступную версию, время проверки, изменения из CHANGELOG, число миграций, состояние помощника, ход выполнения по этапам и историю. Кнопки: «Проверить обновления», «Обновить до vX.Y.Z», «Откатить».

- Проверка версий не меняет систему. Обновление и откат требуют повторного ввода пароля разблокировки сейфов (подтверждение действует 5 минут и привязано к сеансу).
- Приложение не имеет доступа к Docker и shell: оно пишет запрос (несколько строк `ключ=значение`) в каталог обмена `DATA_ROOT/updater`. Операции выполняет **помощник обновлений** — служба systemd `arklock-updater-<проект>`, которую ставит `install.sh`. Разрешены только `check`, `update vX.Y.Z`, `rollback`; значения проверяются по строгим шаблонам, ссылки и неизвестные ключи отвергаются, команды запускаются в стерильном окружении. Помощник использует те же сценарии (`update.sh`, `rollback.sh`), что и командная строка.
- Служба: `scripts/updater.sh status | repair | uninstall`. Если помощник остановился посреди операции, при следующем запуске операция помечается как прерванная.
- Результаты: «Обновление выполнено», «Не удалось собрать новую версию, работающая версия не затронута», «Выполнен возврат на прежнюю версию», «База данных восстановлена из копии».

## Автоматические проверки и обновление

Администрирование → Система → «Обновления» → «Автоматические обновления».

- **Проверка** новой версии выполняется автоматически каждые 30 минут (включена по умолчанию). Она только узнаёт, есть ли выпуск; ничего не устанавливает. На экране видны время последней проверки и ориентировочно следующей.
- **Установка** выключена по умолчанию. Включая её, администратор выбирает время (например, 00:00) и вводит свой пароль разблокировки сейфов: установка идёт без человека, поэтому согласие подтверждается отдельно. Время считается по часовому поясу сервера.
- Раз в сутки в заданное время, если есть новая **стабильная** версия (предварительные не ставятся) и нет другой операции, Arklock просит помощника выполнить то же штатное обновление, что и кнопка «Обновить»: проверка подписей и свободного места, контрольная копия, миграции, проверка работы после обновления, автоматический откат при сбое.
- Если установка не удалась, повторной попытки в тот же день нет; результат виден в журнале и истории обновлений. Без запущенного помощника ничего не происходит.
- Планировщик можно отключить на уровне сервера переменной `AUTO_UPDATE=off` (для стендов и тестов); политика администратора при этом сохраняется.

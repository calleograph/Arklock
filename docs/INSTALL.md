# Установка

Статус проверки: установка, повторный запуск, профиль shared-host, зашифрованное резервное копирование и восстановление автоматически проверяются в CI на чистом раннере Ubuntu 24.04 (см. `.github/workflows/ci.yml`, задачи `installer` и `shared-host`). **Debian 12 и реальный сервер с перезагрузкой пока не проверялись.**

## Требования

- Ubuntu 22.04 или 24.04 LTS, либо Debian 12; архитектура x86_64 или aarch64; root-доступ.
- От 1 ГБ оперативной памяти, от 3 ГиБ свободного места в каталоге данных.
- Доступ в интернет (пакеты, Docker, репозиторий). Для закрытого контура — см. раздел «Ограничения».

## Установка одной командой

Одна команда (последний релиз):

```bash
curl -fsSL https://github.com/calleograph/arklock/releases/latest/download/install.sh | sudo bash
```

Если сначала хотите прочитать и проверить установщик:

```bash
curl -fsSLO https://github.com/calleograph/arklock/releases/latest/download/install.sh
curl -fsSLO https://github.com/calleograph/arklock/releases/latest/download/SHA256SUMS
sha256sum --ignore-missing -c SHA256SUMS      # контрольная сумма install.sh
less install.sh                               # просмотрите, что будет выполнено
sudo bash install.sh                          # либо: sudo bash install.sh --ref vX.Y.Z
```

Установщик не исполняет содержимое ветки `main`: по умолчанию берётся последний релизный тег, а установка непомеченной ветки требует явного `--allow-unreleased`. Код релиза загружается из репозитория, готовый образ — из GHCR (`ghcr.io/calleograph/arklock:<версия>`), если его метка коммита совпадает с загруженным кодом; иначе образ собирается на сервере. Отключить загрузку образа: `ARKLOCK_PULL_RELEASE_IMAGE=0`.

## Что делает установщик

1. Проверяет ОС, архитектуру, память, место, права.
2. Определяет профиль: **standalone** (отдельный сервер) или **shared-host** (на сервере уже работают другие приложения). Выбор можно задать `--profile`.
3. Устанавливает недостающие пакеты и Docker Engine с Compose Plugin — только в профиле standalone.
4. Подбирает свободный порт (8080 и выше) и адрес прослушивания (см. ниже), создаёт каталоги, файл конфигурации `/etc/arklock/arklock.env` (права 600) со случайными секретами и ключ резервного шифрования `/etc/arklock/backup.key`.
5. Собирает образ, запускает PostgreSQL и приложение отдельным compose-проектом, применяет миграции.
6. Устанавливает помощника обновлений (служба systemd), выполняет `scripts/verify.sh` и печатает адрес и **одноразовый код настройки** для создания первого администратора.

Повторный запуск безопасен: секреты, тома и данные не пересоздаются.

### Как пользователи будут открывать Arklock

Браузер выполняет шифрование (мастер-пароль, ключи) только в защищённом контексте: **по HTTPS или на `localhost`**. Поэтому установка считается законченной не тогда, когда запущены контейнеры, а когда понятно, как открыть Arklock безопасно. Установщик спрашивает об этом первым (при запуске с терминалом и без `--yes`) и в итоге называет **два состояния отдельно**: «Технически: готов» (контейнеры работают, проверки пройдены) и «Первый вход: готов / готов локально / не готов».

| Режим (`--access`) | Когда подходит | Что нужно | Что делает установщик |
| --- | --- | --- | --- |
| `local` (по умолчанию) | проверка, пилот, первая учётная запись до настройки HTTPS | ничего: ни домена, ни сертификата | приложение слушает только `127.0.0.1`; первый вход на самом сервере или через SSH-туннель (команда печатается) |
| `https` | HTTPS прямо на этом сервере | имя сервера (`--domain`), режим сертификата (`--https letsencrypt\|self-signed\|existing`) | настраивает Nginx и сертификат (`scripts/proxy.sh`); в профиле shared-host Nginx не меняется, создаётся пример конфигурации |
| `proxy` | HTTPS уже есть на корпоративном reverse proxy или WAF | публичный адрес `--url https://…`; где стоит прокси — `--bind` | сохраняет публичный адрес, адрес и порт приложения, число доверенных прокси и **печатает, что настроить на стороне прокси** (upstream, заголовки, размер тела, таймауты) |

Без `--access` режим выводится из остальных параметров: `--https` → `https`, `--url https://…` → `proxy`, иначе `local` (так работала установка и раньше; изменилась итоговая справка). Сочетания, которые не имеют смысла (`--access proxy` без `--url`, `--url` по `http://` вне localhost, `--access local` вместе с `--https`), отклоняются сразу, до любых изменений, и сообщение говорит, чего не хватает.

**Режим по умолчанию — `local`:** он безопасен (наружу ничего не открывается), не требует домена и сертификата, и первая учётная запись создаётся сразу: `ssh -L 8080:127.0.0.1:8080 <пользователь>@<сервер>`, затем `http://localhost:8080` (для браузера `localhost` — защищённый контекст). Остальным сотрудникам нужен HTTPS: режим меняется **без переустановки и потери данных** (см. «Изменить способ доступа»).

Где слушает приложение (параметр `--bind`, хранится в `APP_BIND` файла `/etc/arklock/arklock.env`; значение сохраняется при повторной установке):

| `--bind`            | Адрес прослушивания                        | Когда подходит                                            |
| ------------------- | ------------------------------------------ | --------------------------------------------------------- |
| `local` (по умолчанию) | `127.0.0.1`                             | reverse proxy (Nginx, Nginx Proxy Manager) на этом же сервере |
| `lan`               | IP сервера в локальной сети                | прокси или WAF на другом сервере локальной сети            |
| `all`               | `0.0.0.0`                                  | прокси в Docker-сети; ограничьте порт фаерволом            |
| `АДРЕС`             | адрес, назначенный серверу                 | несколько сетевых интерфейсов                              |

Адрес хранится в `APP_BIND`, а не в `compose.yaml`: файлы программы менять не нужно, и обновления от этого не блокируются. Если вы всё же правили `compose.yaml` вручную (так делали версии 1.0.x), обновление перенесёт адрес в `APP_BIND` автоматически — см. [устранение неполадок](TROUBLESHOOTING.md).

Примеры:

```bash
# HTTPS на этом сервере (Let's Encrypt): установщик настроит Nginx
sudo bash install.sh --access https --https letsencrypt --domain arklock.example.com --email admin@example.com

# за корпоративным reverse proxy или WAF на другом сервере локальной сети
sudo bash install.sh --yes --access proxy --url https://arklock.example.com --bind lan

# только проверка: ничего наружу не открывается
sudo bash install.sh --yes --access local
```

**Прокси или WAF.** Адрес, на который прокси направляет запросы, — `http://<адрес приложения>:<APP_PORT>`. Прокси должен передавать `Host`, `X-Forwarded-For` и `X-Forwarded-Proto: https`, пропускать тела запросов до 32 МБ, не буферизовать ответы (таймаут чтения от 10 минут) и не менять путь `/api/v1/…`. `TRUSTED_PROXY_HOPS` равен числу прокси между клиентом и приложением (по умолчанию 1). Полный перечень печатается установщиком и командой `scripts/access.sh proxy-help`.

### Проверки доступа

`scripts/access.sh check` (и итог установки в режимах `https` и `proxy`) проверяет по реальным запросам к публичному адресу: имя разрешается, сертификат действителен, ответ принадлежит этому экземпляру (совпадает сборка), приложение видит соединение как HTTPS (прокси передаёт `X-Forwarded-Proto` и приложение ему доверяет), узел запроса совпадает с `APP_PUBLIC_URL`, первая учётная запись уже создана или нет. Для каждой найденной ошибки названа причина и исправление (например, `proxy_set_header X-Forwarded-Proto $scheme;` или `scripts/access.sh set proxy --url … --hops 1`).

Корпоративный адрес часто виден только из внутренней сети. Если имя не разрешается или порт не отвечает с самого сервера, это **не считается ошибкой настройки**: проверка завершается кодом 2 («не удалось проверить») и объясняет, что выполнить её нужно изнутри сети. Внешней проверки HTTPS установщик не требует.

### Изменить способ доступа без переустановки

```bash
scripts/access.sh status                      # что настроено и что осталось сделать
scripts/access.sh check                       # проверки публичного адреса и прокси
scripts/access.sh proxy-help                  # что настроить на прокси или WAF
sudo scripts/access.sh set local              # только этот сервер (адрес и прежний публичный адрес снимаются)
sudo scripts/access.sh set proxy --url https://arklock.example.com [--bind lan] [--port 8080] [--hops 1]
sudo scripts/access.sh set https --domain arklock.example.com [--mode letsencrypt|self-signed|existing]
```

Данные, секреты и тома не затрагиваются. Прежний файл настроек копируется в `<каталог данных>/config-backups`, приложение пересоздаётся только если параметры изменились, а уже заданный адрес не заменяется молча: нужен интерактивный ответ или `--yes`. Если после замены приложение не стало готовым, сообщение указывает копию, из которой можно вернуться.

Страница входа на небезопасном адресе (`http://<IP>`) тоже объясняет причину: предлагает безопасный публичный адрес (если он задан) и команду SSH-туннеля.

### Профиль shared-host

Установщик **не устанавливает** Docker и пакеты, не меняет Nginx, чужие контейнеры, чужие порты и настройки системы. Занятый порт не занимается (`--port` на занятый порт — отказ без побочных эффектов). Если Docker или утилиты отсутствуют, установщик сообщает, что нужно поставить вручную.

## Параметры

`--profile`, `--dir` (по умолчанию `/opt/arklock`), `--data` (по умолчанию `/var/lib/arklock`), `--config`, `--project`, `--port`, `--bind`, `--access`, `--url`, `--https`, `--domain`, `--ref`, `--repo`, `--allow-unreleased`, `--yes`, `--dry-run`. Подробности: `./install.sh --help`.

## Первый вход

Итог установки называет адрес и состояние: «Первый вход: готов» (HTTPS настроен), «готов локально» (`http://localhost:<порт>` на сервере или через SSH-туннель) либо «не готов» (приложение доступно по сети без HTTPS: браузер не даст создать учётную запись, итог говорит, какой командой это исправить). Откройте адрес, создайте первую учётную запись, введите код настройки (он хранится в `arklock.env` как `BOOTSTRAP_TOKEN` и нужен только для первой записи), сохраните показанный **ключ восстановления**.

## HTTPS и reverse proxy

Приложение слушает только `127.0.0.1`; наружу смотрит Nginx с HTTPS.

**Автоматически** (профиль standalone, Debian/Ubuntu):

```bash
sudo ./install.sh --https letsencrypt --domain arklock.example.com --email admin@example.com
# или позже, на работающей установке:
sudo scripts/proxy.sh setup --domain arklock.example.com --mode letsencrypt --email admin@example.com
```

Режимы: `letsencrypt` (бесплатный сертификат Let's Encrypt; нужны публичное DNS-имя этого сервера и открытые порты 80 и 443; продление — таймером certbot с перезагрузкой Nginx), `self-signed` (закрытые сети и проверки; браузер предупредит, пока сертификат не добавлен в доверенные), `existing` (свой сертификат: `--cert`, `--key`; проверяется, что ключ подходит к сертификату и срок не истёк). Сценарий ставит пакеты `nginx` (и `certbot`), пишет `/etc/nginx/conf.d/arklock-<проект>.conf`, проверяет `nginx -t` (при ошибке возвращает прежнюю конфигурацию), записывает в `arklock.env` `APP_PUBLIC_URL=https://домен` и `TRUSTED_PROXY_HOPS=1` и перезапускает приложение. Настройка прокси: перенаправление http → https, HSTS, TLS 1.2/1.3, передача реального адреса клиента (`X-Forwarded-For` перезаписывается — подделать его нельзя), отключённая буферизация больших ответов, `client_max_body_size 32m` (вложения передаются частями).

Управление: `scripts/proxy.sh status` (конфигурация, `nginx -t`, срок сертификата, продление), `renew`, `remove`, `print` (вывести конфигурацию, ничего не меняя).

**Общий сервер (профиль shared-host)**: Nginx, уже обслуживающий другие сайты, не изменяется — `install.sh --https … --domain …` лишь создаёт пример конфигурации `nginx-arklock.conf.example` рядом с `arklock.env`; `scripts/proxy.sh print --domain …` печатает её, подключите результат сами. Если Nginx уже обслуживает другие сайты, `setup` отказывается работать без `ARKLOCK_PROXY_FORCE=1`.

**Проверено**: в CI на Ubuntu 24.04 — самоподписанный режим с настоящим Nginx (перенаправление, заголовки, `status`, повторная настройка, удаление); на Debian 12 — синтаксис конфигурации для Nginx 1.22 (`http2` в директиве `listen`). **Не проверено автоматически**: получение сертификата Let's Encrypt (нужны публичное DNS-имя и доступ из интернета) и продление certbot — используются стандартные команды `certbot certonly --webroot` и `certbot.timer`; перед боевым использованием выполните `scripts/proxy.sh setup --staging` (тестовый центр сертификации) и `certbot renew --dry-run`.

## Ограничения

- Готовый образ скачивается из GHCR, если метка коммита совпадает с кодом релиза; иначе образ собирается на сервере. Проверка digest образа не реализована.
- Установка в закрытом контуре (локальный registry, офлайн-пакет) не реализована.

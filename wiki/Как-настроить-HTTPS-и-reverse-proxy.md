# Как настроить HTTPS и reverse proxy

> Относится к версии 1.86.0 · проверено 2026-10-28 · уровень проверки 2 (самоподписанный режим проверяется в CI с настоящим Nginx); Let's Encrypt — уровень 1

*Тип страницы: практическое руководство.*

Для кого: системный администратор. Результат: Arklock открывается по HTTPS, а приложение слушает только `127.0.0.1`. Нужно заранее: установленный Arklock ([Установка](Установка)).

## Почему HTTPS обязателен

Браузер выполняет шифрование только в защищённом контексте: по HTTPS или на `localhost`. По `http://192.168.x.x` вход, регистрация и разблокировка не работают, и Arklock показывает причину.

## Выберите способ

| Ситуация | Способ | Команда |
| --- | --- | --- |
| Есть имя сервера, прокси ещё нет | HTTPS на этом сервере | `scripts/access.sh set https --domain arklock.example.com` |
| HTTPS уже даёт корпоративный reverse proxy или WAF | Внешний прокси | `scripts/access.sh set proxy --url https://arklock.example.com [--bind lan]` |
| Нужно только проверить Arklock | Локально | `scripts/access.sh set local`, затем SSH-туннель и `http://localhost:<порт>` |

Эти команды можно запускать и сразу при установке (`--access https|proxy|local`), и позже на работающем экземпляре: данные не затрагиваются. `scripts/access.sh status` показывает, что настроено и что осталось сделать, `scripts/access.sh check` проверяет публичный адрес и прокси, `scripts/access.sh proxy-help` печатает, что должен делать прокси (upstream, заголовки `Host`, `X-Forwarded-For`, `X-Forwarded-Proto`, размер тела 32 МБ, таймауты).

Если адрес доступен только из внутренней сети, проверка с сервера может не дотянуться до него: она ответит «не удалось проверить» (код 2), а не ошибкой. Повторите `scripts/access.sh check` изнутри сети.

## Вариант 1. Установщик настраивает Nginx

Профиль `standalone`, Debian или Ubuntu.

```bash
sudo ./install.sh --https letsencrypt --domain arklock.example.com --email admin@example.com
```

Или на работающей установке:

```bash
sudo scripts/proxy.sh setup --domain arklock.example.com --mode letsencrypt --email admin@example.com
```

Режимы:

| Режим | Когда | Требования |
| --- | --- | --- |
| `letsencrypt` | Публичное имя | Публичный DNS этого сервера, открытые порты 80 и 443 |
| `self-signed` | Закрытая сеть и проверки | Браузер предупредит, пока сертификат не добавлен в доверенные |
| `existing` | Свой сертификат | `--cert` и `--key`; проверяется, что ключ подходит и срок не истёк |

Ожидаемый результат: `scripts/proxy.sh status` показывает конфигурацию, результат `nginx -t`, срок сертификата и состояние продления.

Скрипт ставит `nginx` (и `certbot`), пишет `/etc/nginx/conf.d/arklock-<проект>.conf`, проверяет `nginx -t` (при ошибке возвращает прежнюю конфигурацию), записывает в `arklock.env` значения `APP_PUBLIC_URL=https://домен` и `TRUSTED_PROXY_HOPS=1` и перезапускает приложение. Настройка прокси: перенаправление http на https, HSTS, TLS 1.2/1.3, передача реального адреса клиента, `client_max_body_size 32m`.

> **Предупреждение.** Получение сертификата Let's Encrypt и его продление автоматически не проверялись. Перед боевым запуском выполните `scripts/proxy.sh setup --staging` и `certbot renew --dry-run`.

## Вариант 2. Свой reverse proxy

1. Установите Arklock с адресом, доступным прокси: `--bind lan` или `--bind all` ограничьте фаерволом.
2. Настройте на прокси терминирование HTTPS и передачу `X-Forwarded-For` и `X-Forwarded-Proto`.
3. Адрес для проксирования: `http://<адрес сервера>:<APP_PORT>`.
4. Задайте `TRUSTED_PROXY_HOPS` равным числу прокси перед контейнером (по умолчанию 1; `0` — прокси нет, заголовок `X-Forwarded-For` игнорируется). Доверяется ровно указанное число звеньев справа, поэтому адрес, добавленный вашим прокси, не подделать. Вместо числа можно задать список адресов прокси в «Администрирование → Защита веб-приложения → IP-адреса и подсети». Проверьте там же строку «Ваш адрес, как его видит Arklock».
5. Не публикуйте порт приложения наружу напрямую.
6. Укажите публичный адрес в панели: «Администрирование → Настройки сервера → Сеть и доступ».

## Общий сервер (shared-host)

Nginx, уже обслуживающий другие сайты, не изменяется. Установщик создаёт пример `nginx-arklock.conf.example` рядом с `arklock.env`; `scripts/proxy.sh print --domain …` печатает конфигурацию. Подключите её сами. Если Nginx уже обслуживает сайты, `setup` отказывается работать без `ARKLOCK_PROXY_FORCE=1`.

## Управление

```bash
sudo scripts/proxy.sh status
sudo scripts/proxy.sh renew
sudo scripts/proxy.sh remove
sudo scripts/proxy.sh print --domain arklock.example.com
```

## Публичный адрес и что от него зависит

Публичный адрес в панели главнее `APP_PUBLIC_URL`, применяется без перезапуска, нужен для SSO, SAML и ссылок в письмах. Ключи доступа (WebAuthn) привязаны к имени узла: при смене адреса прежние перестанут подходить. Изменение требует подтверждения паролем разблокировки сейфов.

## Типичные ошибки

- С другого компьютера страница не открывается: запустите установщик снова с `--bind lan`.
- IP клиента в журнале неверный (виден адрес прокси): проверьте `TRUSTED_PROXY_HOPS` или список доверенных прокси; страница «Защита веб-приложения» показывает адрес соединения и заголовок.

См. [Диагностика](Диагностика).

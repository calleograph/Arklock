# Как настроить SSO (OpenID Connect и SAML)

> Относится к версии 1.80.0 · проверено 2026-10-28 · уровень проверки 2 (`sso.test.ts`, `saml.test.ts`, браузерные сценарии). **Entra ID, ADFS, Okta, Keycloak и другие реальные провайдеры не проверялись**: интеграция проверена на тестовом провайдере.

*Тип страницы: практическое руководство.*

Для кого: администратор и интегратор. Результат: сотрудники входят через корпоративного провайдера. Нужно заранее: публичный HTTPS-адрес Arklock (Администрирование → Настройки сервера → Сеть и доступ или `APP_PUBLIC_URL`) — без него SSO и SAML включить нельзя. Права полного администратора.

Провайдер подтверждает, кто пользователь. **Пароль разблокировки сейфов остаётся отдельным**: провайдер и сервер не получают доступа к содержимому.

## OpenID Connect

1. Откройте «Администрирование → Интеграции → Единый вход (SSO)».
2. Скопируйте **адрес возврата** `<публичный адрес>/api/v1/auth/sso/callback` и зарегистрируйте его у провайдера.
3. Укажите издателя (issuer), идентификатор и секрет клиента, при необходимости — допустимые домены почты.
4. Нажмите «Проверить провайдера». Ожидаемый результат: прочитан документ discovery, сверен издатель, загружены ключи подписи.
5. Сохраните и включите.

Защита: код авторизации с PKCE (S256), `state`, `nonce`, проверка подписи id_token (только RS256/RS384/RS512/ES256/ES384; `none` и HMAC отвергаются), издателя, аудитории и срока; непроверенная почта и домены вне списка отвергаются. Провайдер без HTTPS допускается только по явному разрешению.

## SAML 2.0

1. Откройте «Администрирование → Интеграции → SAML 2.0». Вверху показаны данные Arklock: Entity ID, адрес приёма ответов ACS (HTTP-POST), адрес единого выхода и ссылка на метаданные. Метаданные доступны без входа.
2. Зарегистрируйте Arklock у провайдера по этим данным.
3. Импортируйте метаданные провайдера (вставьте XML или укажите адрес). Форма заполнится.
4. Настройте сопоставление: атрибуты почты, имени, идентификатора (по умолчанию NameID), групп; сопоставление групп провайдера и групп Arklock; необязательный список групп, которым разрешён вход; домены почты.
5. Нажмите «Проверить настройку»: проверяются сертификаты (срок, размер ключа), доступность адреса входа, построение запроса.
6. Сохраните и включите.

Подпись запроса и зашифрованные утверждения: кнопка «Создать сертификат поставщика услуг» создаёт RSA-2048 на 10 лет; закрытый ключ хранится запечатанным и не возвращается API. После замены сертификата загрузите новые метаданные у провайдера.

### Что проверяется при входе

Подпись (по настроенным сертификатам, `KeyInfo` из документа не используется), SHA-1 отвергается по умолчанию, статус и издатель, `NotBefore`/`NotOnOrAfter`, аудитория и ACS, `InResponseTo`, одноразовость утверждения, привязка билета к браузеру, ограничение попыток, домен почты. Ответы по инициативе провайдера отвергаются по умолчанию.

### Группы и отзыв

- Группы провайдера пересчитываются при каждом входе: исключённый теряет членство и права.
- Если задан список групп для входа, а пользователь ни в одну не входит, вход отклоняется и его сеансы завершаются.
- Единый выход со стороны провайдера завершает все сеансы пользователя; выход из Arklock завершает только сеансы Arklock.
- Параметр «Предельная длительность сеанса вошедших по SAML» заставляет заново спросить провайдера.

## Ограничения

- Для SAML настраивается один провайдер; Artifact-привязка не поддерживается.
- Метаданные по адресу читаются без проверки подписи: сверяйте отпечатки сертификатов.
- Атрибуты SSO и SAML в карточку сотрудника не переносятся.
- HTTP-Redirect для единого выхода реализован, но автотестом не покрыт.

## Типичные ошибки

- Вход остановлен с причиной `idp_cert_expired`: все сертификаты провайдера истекли. Загрузите новые.
- Журнал событий: `auth.saml.failed` с кодом причины.
